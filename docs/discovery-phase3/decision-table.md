# SAAX Discovery Phase 3 — Decision Table (additions)

**Date:** 2026-11-06 · Extends `docs/discovery-phase2/decision-table.md`

| # | Decision | Choice | Rationale |
|---|---|---|---|
| D39 | Preflight storage engine | File-backed append-only journal (`endpoint/proposal-store.js`) | No runtime-DB dependency for the isolated endpoint + MCP; restart-safe (fsync before ack); append-only = crash leaves either old-complete or new-line (torn tail truncated on load, never merged). Supabase/DB is the documented Phase-4 deployment path; NOT assumed live. |
| D40 | Idempotency decision point | The store's `persist()` is the SINGLE atomic op (no separate acquire) | A separate acquire+persist pair allows all concurrent acquires to pass before any persist → contradictory records. Single serialized persist with compare-and-swap inside the append is race-free. |
| D41 | Duplicate vs conflict | Same scoped key + same digest → duplicate (same unexpired proposal); same key + different digest → `DSC_NONCE_CONFLICT` | Spec §6.5/§7.4: identical retries retrieve the same operation; changed requests using the same nonce conflict. Duplicate returns the ORIGINAL proposal (never a new one). |
| D42 | Expired proposal handling | Expired duplicates stay expired; NO silent fresh re-issue; fresh proposal requires fresh nonce; explicit `expire()` + new issuance is operator-controlled | "Offer valid until expiry; stale-on-change" — never substitute new terms beneath an existing signature, and never auto-replace an expired agreement representation. |
| D43 | Proposal validity window | 1 hour from issuance (`DEFAULT_PROPOSAL_TTL_SECONDS = 3600`) | Matches the spec's example semantics (offer valid until expires, revalidated at commit time); long enough for a buyer to review, short enough to bound staleness. |
| D44 | Proposal trust axes | `trust.selfSigned=true, authenticated=false, independentConformance=false, anchors:[]` in every Phase-3 proposal | The preflight signs with the provider key; authentication of that key is the Phase-2 resolver's job (configured-key anchor). The proposal itself never claims authenticated status. |
| D45 | Normalization authority | `requestDigest` is over the NORMALIZED request (RFC 8785 JCS sha256); every normalization is explicit in returned terms | Spec §6.4. The buyer recomputes over its original request; mismatch → counter-offer, not acceptance. |
| D46 | Financial-combination gating | Exact match against `supportedCombinations[]` (network+asset+rail+mode) — syntax alone never suffices | Spec §4.3; `DSC_INVALID_COMBINATION` on any non-listed tuple. |
| D47 | Schema gating | Requested schema (id+version+digest) must appear among the capability's declared schemas | `DSC_SCHEMA_MISMATCH`; protects against digest substitution. |
| D48 | Truthful interface | Fixture profile declares `prepareCommitment:true` ONLY because the endpoint + MCP tool are implemented (isolated/test) | No-claim rule: never declare an interface that does not exist. Production publication still requires the approved release process. |
| D49 | MCP registration | Registered as `prepare_commitment` with zod inputSchema mirroring the request; description says nonbinding + free; NOT advertised as live | Same validation/signing/persistence core as HTTP; do not claim availability until the corresponding public endpoint is deployed + tested. |
| D50 | Financial side-effect guard | Preflight path invokes ONLY store + signer; tests spy that no payment/custody/commitment/execution call occurs and no such field exists in the proposal | Requirement §6: absence of financial effects must be PROVEN, not inferred from a 200. |
