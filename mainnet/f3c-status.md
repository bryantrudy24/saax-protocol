## 9. Funding-deadline approval discrepancy — DECISION BRIEF for owner approval (item 3 of the closeout directive)
**The question being decided:** what is the correct funding-time gate for the V3 custody candidate? The two candidates:

- **Option A — keep the implemented funding rule `T_fund < resolutionDeadline`** (the V3 candidate as built: `f3a-custody-v3-spec.md` line 32 `Fund | fundingEnabled must be true | T_fund < resolutionDeadline | block.timestamp < resolutionDeadline | AfterResolutionDeadline, FundingDisabled`).
- **Option B — change the funding rule to `T_fund < finalCutoff`** (funding allowed all the way up to the final cutoff, the buyer-protective timeout boundary).

**Practical consequences:**
- **Option A (implemented):** funding is permitted only while the evaluator/mutual decision window is open (`T_fund < resolutionDeadline`). After `resolutionDeadline`, a position can no longer be funded; ordinary evaluator/mutual settlement is likewise unavailable after `resolutionDeadline`. If `resolutionDeadline < finalCutoff` (the intentional gap), then during `[resolutionDeadline, finalCutoff)` a position cannot be funded AND cannot be ordinarily resolved — only the timeout refund at/after `finalCutoff` exits an already-funded position. Funding into this gap is rejected, which is conservative (no new funds enter a window where only timeout recovery remains). Consequence: the buyer's funds cannot be committed into a position whose resolution window has already closed; the only later exit for anything already funded is timeout refund.
- **Option B (`T_fund < finalCutoff`):** funding remains available through the gap until the final cutoff. During `[resolutionDeadline, finalCutoff)`, new funds can still enter escrow even though ordinary evaluator/mutual settlement is unavailable and only later timeout recovery (at/after `finalCutoff`) remains. Consequence: a buyer could fund a position during the gap knowing the only exit is a timeout refund to themselves — functionally a deposit with a fixed lock until cutoff, with NO possibility of the seller ever being paid (evaluator/mutual cannot resolve). That is an economically odd position: seller can never receive funds from a gap-funded escrow, yet the escrow exists and ties up the buyer's liquidity until cutoff.
- **Recommendation: Option A** (keep `T_fund < resolutionDeadline`). It is the implemented rule, it is conservative, and it avoids the economically meaningless "fund into the gap where only timeout refund remains" position. Changing to Option B would permit a class of escrow that can never reach the seller — a silent economic change with no compensating buyer/seller benefit. The F3A spec line ("funding at/after resolutionDeadline rejected") already codifies Option A; the missing piece is an **authoritative approval record** for that policy, not a rule change.

**Authoritative approval record search:** an explicit search of the repo (decision logs, policy docs, addenda, readiness/status docs, agreement templates) found **NO independent authoritative approval record** for either funding rule — no signed/dated owner decision, no approval log entry, no addendum clause stating "funding permitted only before resolutionDeadline" as an approved economic term. The ONLY citation is the F3A spec line itself (`f3a-custody-v3-spec.md:54`: "closes the D8 admissibility gap per the approved policy 'funding at/after resolutionDeadline rejected'"), which asserts an approved policy without pointing to a separate record. `mainnet/f3c-status.md` §9 prior text and `mainnet/release-candidate-gap-assessment.md` confirm: "No separate authoritative approval record beyond that spec line was located this review."

**RESOLVED 2026-10-19:** the owner approved Option A (`T_fund < resolutionDeadline`); authoritative record `mainnet/funding-rule-approval.md`. No contract change was made; this only records the approval.
